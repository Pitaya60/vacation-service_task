## Решения

### D1 — Запуск без Docker
- **Проблема:** Docker Desktop на машине не запустился; первый план (Node + Docker) делал запуск зависимым от него.
- **Альтернативы:** починить Docker; ставить PostgreSQL вручную; встроенный PostgreSQL через pip.
- **Решение:** pip-пакет со встроенным PostgreSQL поднимается сам при старте backend; для внешней БД — `DATABASE_URL`.
- **Компромисс:** данные в `.pgdata/`, нельзя запускать от администратора Windows; для production — обычный Postgres.
- **Проверка:** запуск и 27 тестов (позже 29 на двух БД) прошли в сессии Claude (Linux). На Windows пользователя встроенный Postgres **не запустился** (см. D9, D10, D11, пункт 15).

### D2 — Python/FastAPI вместо Node
- Требование пользователя. FastAPI даёт валидацию запросов и `/docs`; SQL пишется напрямую, без ORM: нужны `on conflict do nothing`, пересечение интервалов, `pg_notify`.

### D3 — Остаток не хранится, а считается функцией `accrued()`
- Смена даты выхода пересчитывает всё без миграций данных. Проверено тестом `test_hire_date_change_recalculates`.

### D4 — «Ровно одно» уведомление держит БД
- `unique(type, vacation_id, recipient_id)` + `on conflict do nothing`. Проверено: гонка двух согласований и двойной вызов `remind()` дают по одному уведомлению.

### D5 — SSE поверх Postgres LISTEN/NOTIFY
- Нужен только поток сервер→клиент; NOTIFY работает и при нескольких процессах. Проверено e2e-тестом на две сессии.

### D6 — Согласование атомарно
- `update ... where status='pending' returning` — второй одновременный запрос получает 409.

### D7 — Запуск через start.bat (Python 3.10–3.12) — заменено D9
- **Проблема:** у пользователя страницы не запустились. Предполагалось: для Python 3.13/3.14 нет колеса `pgserver` под Windows, а `.ps1` и `npm` блокирует политика выполнения PowerShell.
- **Решение:** `start.bat` (cmd, без политик) ищет Python, проверяет Node, оставляет окна открытыми при ошибке; frontend показывает понятную ошибку, если backend недоступен.
- **Итог:** ограничение «только 3.10–3.12» снято в D9. Версия Python не была единственной причиной (см. пункт 15).

### D8 — Календарь месячной сеткой
- Строки — сотрудники, столбцы — дни, цвет по статусу; перерисовывается по SSE. Позже календарь переделан в полосы по месяцу и просмотрен в браузере (D12, пункты 27–28).

### D9 — Переход на форк pixeltable-pgserver, поддержка Python 3.13/3.14
- **Проблема:** у пользователя Python 3.14; у оригинального `pgserver` нет сборки под Python 3.13+ для Windows.
- **Альтернативы:** поставить Python 3.12 рядом; перейти на внешний PostgreSQL.
- **Решение:** `pixeltable-pgserver` (тот же API, в `db.py` оставлен запасной импорт оригинала); `start.bat` принимает Python 3.10+.
- **Проверка:** 27 тестов на форке прошли в среде Claude (Linux, Python 3.12). На Python 3.14 пакет установился у пользователя (`pixeltable-pgserver 0.6.0`), но встроенный Postgres на его Windows не запустился (пункт 15).
- **Закрыто:** путь `pginstall18` оказался правдой: в среде Claude `select version()` вернул PostgreSQL 18.4. Надпись «PostgreSQL 16» в README, `docs/DATABASE.md` и `db.py` была неверной и исправлена.

### D10 — Понятная ошибка при падении встроенного PostgreSQL
- **Проблема:** при падении `initdb` пользователь видел длинный traceback без объяснения.
- **Решение:** `db.py` обновлён, чтобы сообщение объясняло причину и предлагало `DATABASE_URL` как запасной путь.
- **Статус:** подтверждено на Windows пользователя: при сбое выводится новое сообщение (лог пользователя, пункт 19). Сам сбой оно не устраняет.

### D11 — Запасной режим на SQLite
- **Проблема:** на Windows пользователя встроенный `postgres.exe` не запускается (`0xC0000135`) даже в свежем `backend\.venv`; причину (вероятно, нет Visual C++ Redistributable) удалённо проверить нельзя, а без базы не стартует весь backend.
- **Альтернативы:** ждать, пока пользователь поставит Redistributable или обычный PostgreSQL (`DATABASE_URL`); оставить только PostgreSQL.
- **Решение:** порядок выбора БД: `DATABASE_URL` → встроенный PostgreSQL → SQLite (`.vacation.sqlite3`). Переход на SQLite только при сбое встроенного Postgres или при `VAC_DB=sqlite`; при заданном `DATABASE_URL` запасного режима нет. О режиме сообщают консоль, `/api/v1/health` (`db`, `warning`) и жёлтая полоса в интерфейсе.
- **Что изменено в коде:** `db.connection()` и `db.notify()` вместо прямого пула и `pg_notify`; список заявок собирается без `json_agg`; схема для SQLite подменяет `serial`/`timestamptz`; даты читаются как `date`.
- **Компромисс:** задание предпочитает PostgreSQL, SQLite — запасной путь; в нём нет `LISTEN/NOTIFY` (используется вызов в процессе, значит один процесс backend) и нет проверки на параллельной нагрузке.
- **Проверка:** те же 29 тестов проходят на PostgreSQL 18.4 и на SQLite (среда Claude, Linux). На Windows пользователя запасной режим **не проверен**.

### D12 — Новый интерфейс: Montserrat, сине-жёлтая палитра, экраны по ролям
- **Запрос:** шрифт Montserrat, понятный UX; для HR жёлтый и синий цвета.
- **Решение:** шрифт через npm-пакет `@fontsource-variable/montserrat` (кириллица, работает без интернета, не зависит от Google Fonts). Токены цвета в `styles.css`: синий `#2347D0`, жёлтый `#FFC400`, тёмно-синий текст `#0B1B4D`. У HR жёлтая шапка и жёлтые акценты, у остальных синяя шапка; в календаре синий — согласовано, жёлтый со штриховкой — на рассмотрении (смысл цвета не зависит от роли, штриховка помогает при плохом различении цветов).
- **UX:** вкладки по ролям, вместо одной длинной страницы; демо-вход одной кнопкой; ошибка правил дробления показывается в самой форме; причина отказа обязательна и вводится в поле, а не в `prompt()`; перенос — режим формы, а не отдельный ввод дат; бейдж числа заявок на вкладке руководителя; пустые состояния с подсказкой, что делать; сессия сохраняется в `sessionStorage` (обновление страницы не разлогинивает, при 401 — возврат на вход).
- **Компромиссы:** формат даты в полях ввода зависит от языка браузера; уведомления показываются списком без пометки «прочитано» (в API нет такого состояния); пересчёт доступного остатка для прогноза берётся с сервера, правила дробления на клиенте не дублируются.
- **Проверка:** `tsc --noEmit` и `vite build` без ошибок; ручной прогон сценариев в Chromium (Playwright) в среде Claude; на Windows пользователя не проверено.

### D13 — Годовой лимит частей
- **Правило:** в календарном году (по дате начала части) не больше 4 частей по заявкам «на рассмотрении» и «согласован»; лимит задан константой `MAX_PARTS_PER_YEAR`. Число 4 выбрано мной как разумное при «до 3 частей в заявке», в задании его нет.
- **Как работает:** `rules.check_year_limit`, вызывается при создании и переносе заявки; отмена освобождает лимит (будущие части удаляются). Сообщение называет год и числа.
- **Проверка:** юнит-тест и тест через API (пятая часть → 422, другой год проходит).

### D14 — Пересмотр заявок после смены даты выхода
- **Альтернативы:** менять статус заявок автоматически (вернуть на согласование или отменить); только пометка у HR (было).
- **Решение:** статусы не меняются, чтобы не отменять согласованный отпуск без решения человека. Сотрудник, его руководитель и все HR получают по одному уведомлению на каждую заявку, которая перестала покрываться накоплением (тот же уникальный ключ, что и у остальных уведомлений); в таблице HR показана причина (`problem`). Несуществующий сотрудник → 404.
- **Компромисс:** при повторной смене даты по той же заявке новое уведомление не придёт (ключ уже занят).
- **Проверка:** `test_hire_change_review_notifies_once_each`, `test_hire_change_without_conflict_sends_nothing`.

### D15 — Версионированные миграции вместо Alembic
- **Причина отказа от Alembic:** в проекте нет SQLAlchemy (SQL пишется напрямую, D2), а Alembic без него неудобен; одни и те же миграции должны работать и на PostgreSQL, и на SQLite.
- **Решение:** файлы `backend/app/migrations/NNN_имя.sql`, применяются при старте по порядку, версии пишутся в `schema_migrations`. `schema.sql` перенесён в `001_init.sql`. Добавлены `002_notification_read.sql` и `003_sessions.sql`.
- **Компромисс:** нет откатов (down) и проверки контрольных сумм файлов.
- **Проверка:** `test_migrations_recorded_once`.

### D16 — Сессии в БД и «прочитано» у уведомлений
- **Сессии:** вместо словаря в памяти — таблица `sessions` (хранится SHA-256 токена, срок 7 дней, `POST /logout`). Перезапуск backend больше не разлогинивает. Реальный перезапуск процесса вручную не проверялся, проверены хранение хеша, выход и просрочка.
- **Уведомления:** `read_at`, `POST /notifications/read`; у колокольчика счётчик, при открытии новые подсвечены.
- **Известное ограничение:** токен передаётся в адресе `/events?token=` (у `EventSource` нет заголовков).

### D17 — Сквозные тесты интерфейса в репозитории
- **Решение:** `e2e/test_ui.py` (Playwright, Chromium): 5 сценариев из ручных прогонов, запуск описан в `e2e/README.md`; результат в `E2E_RESULTS.txt`, скриншоты в `docs/screenshots/`.
- **Компромисс:** тесты не требуют чистой БД, но оставляют в ней тестовые заявки (даты в далёком будущем), поэтому запускать их лучше на временной БД; другие браузеры не проверялись.

### D18 — Переподключение слушателя LISTEN/NOTIFY
- **Проблема:** при обрыве соединения с PostgreSQL поток `_listen` падал с исключением и не поднимался снова; календари перестали бы обновляться без перезагрузки до перезапуска backend. Нашлось по исключению в выводе тестов, которое раньше принимали за шум остановки.
- **Решение:** `_listen` в цикле: подключение, `listen cal`, при ошибке пауза 2 с и повтор. После каждого подключения клиентам рассылается одно событие, чтобы они перечитали данные (во время обрыва события могли потеряться).
- **Проверка:** `test_sse_survives_listener_connection_drop` — соединение слушателя завершается через `pg_terminate_backend`, после чего новая заявка снова доходит по SSE. До исправления тест падал. На SQLite пропускается (там нет LISTEN).
